# Search & AI discovery-file integration

AJNanda generates `/robots.txt`, `/llms.txt`, `/llms-full.txt`, `/ai.txt`, and
`/.well-known/security.txt` dynamically. Do not create physical copies of these files in
the document root; LiteSpeed would serve those copies before WordPress and they would
become stale.

## Apache / LiteSpeed redirects

Place these rules before the standard WordPress rewrite block in the document-root
`.htaccess` file:

```apache
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteRule ^\.well-known/llms\.txt$ /llms.txt [R=302,L,NE]
RewriteRule ^\.well-known/change-password$ /client-portal/ [R=302,L,NE]
</IfModule>
```

The temporary redirects are intentional: they avoid a long-lived browser or CDN cache
while these nonstandard aliases are in use. They may be changed to `R=301` after the
destinations are considered permanent.

## WordPress head discovery

The theme registers this equivalent output on `wp_head`:

```html
<link rel="alternate" type="text/plain" href="https://example.com/llms.txt" title="LLMs.txt">
```

The link is an additional discovery hint. It is not a standardized crawler directive.

## Required response checks

```bash
curl -i https://example.com/robots.txt
curl -i https://example.com/llms.txt
curl -i https://example.com/llms-full.txt
curl -i https://example.com/ai.txt
curl -i https://example.com/.well-known/security.txt
curl -I https://example.com/.well-known/llms.txt
curl -I https://example.com/.well-known/change-password
```

Purge LiteSpeed and Cloudflare caches after deploying or changing redirects. If a
response lacks normal WordPress headers and has an old `Last-Modified` value, remove the
conflicting physical file or disable the host plugin that generated it.

## Hostinger Tools integration

Search & AI → AI Discovery and Discovery Files show Hostinger status only when
Hostinger Tools is loaded or Hostinger's `H_PLATFORM` server signal is present.
The optional adapter is `inc/search-ai/class-hostinger.php`. It reads the public
`Hostinger\Admin\PluginSettings::get_plugin_settings()` accessor and feature
getters defensively. Plugin presence is reported separately from hosting evidence;
a migrated plugin or saved opt-in is not proof of a working Hostinger service.
No Hostinger dependency, option writes, token reads, remote opt-in calls, or plugin
file modifications are introduced. AJNanda's capability ownership and policies
remain authoritative for its existing outputs.

### Reviewed implementation and synchronization decision

Reviewed the WordPress.org Hostinger Tools **3.0.77** release source on 2026-09-09:

- [Release source](https://plugins.svn.wordpress.org/hostinger/tags/3.0.77/)
- `includes/LlmsTxtGenerator/LlmsTxtGenerator.php`, `LlmsTxtFileHelper.php`, and
  `LlmsTxtParser.php`
- `includes/Admin/Jobs/LlmsTxtInjectContentJob.php`
- `includes/Admin/PluginSettings.php`, `Admin/Options/PluginOptions.php`,
  `Rest/SettingsRoutes.php`, `Hooks.php`, and `Mcp/Handlers/EventHandler.php`
- `vue-frontend/src/views/HostingerTools.vue` and `includes/Admin/Assets.php`

Hostinger stores `enable_llms_txt` and `optin_mcp` in its `hostinger_tools` option.
Its generator writes **ABSPATH/llms.txt** through WP_Filesystem, initially listing
published posts/pages/products and then scheduling additional batches. Settings
saves, publication transitions, site title/description changes, and WooCommerce
activation changes can regenerate it. An administrator request can recreate a
missing file while generation is enabled. It does not use AJNanda's curated
Important Pages, discovery eligibility, or Content Access exclusions.

The reviewed generator and file helper have **no complete-content replacement
filter**. Batch-size filters cannot safely replace content. Overwriting after a
settings hook would race later background writes and would not cover every
AJNanda policy/content change. Consequently **automatic synchronization is not
implemented**. AJNanda does not take over Hostinger callbacks or write a second
physical copy. Keep Hostinger's individual **Create LLMs.txt file** toggle off.

Hostinger identifies its files by the marker
`[comment]: # (Generated by Hostinger Tools Plugin)`. Normal generation and deletion
preserve files without that signature. Its UI warns that enabling generation can
replace an external file, although the reviewed generator still checks for a
user-generated file; do not rely on that UI/backend discrepancy for protection.
Disabling generation deletes a signed file through Hostinger's settings-save path.
Back up and review any remaining physical file manually, then purge relevant caches.
AJNanda never deletes or overwrites it.

### Web2Agent consent and endpoint

The adapter links to Hostinger's own Tools menu, where the user uses the individual
**Web2Agent** toggle and completes the native opt-in/consent flow. The reviewed UI
uses the individual toggle as opt-in; no separate Web2Agent consent modal was found.
Future Hostinger consent steps remain intact because AJNanda does not submit the
REST API or write `optin_mcp`. Avoid the LLM Optimization **master toggle**, which
sets both Web2Agent and file generation together.

Hostinger disables this section without `H_PLATFORM` or on its temporary domains
(`hostingersite.com` and `hostingersite.dev`). AJNanda uses hostname suffix checks for
these service domains, with no customer/domain constants. Unsupported plugin APIs
report unknown rather than disabled. Stale opt-in remains visible on migrated sites,
but no available endpoint is advertised without platform/feature evidence.

When opted in on a supported domain, AJNanda displays a **derived**, unverified
HTTPS endpoint using Hostinger's parser convention:
`https://websites-agents.hostinger.com/{site_url hostname}/mcp`.
Hostinger's UI copy action instead uses the browser's `location.host`; installations
with different admin and public domains or ports require particular verification.
The separate Hostinger Agent / WordPress MCP site-management feature is not Web2Agent
and is not enabled by this integration.

Saved opt-in triggers Hostinger notification jobs; it does not prove remote
provisioning succeeded. AJNanda does not probe or claim health of the MCP endpoint
and does not add it to curated llms.txt automatically. Confirm provisioning and
Content Access / robots policy enforcement using a real Hostinger account and MCP
client. AJNanda's local exclusions cannot guarantee remote-service enforcement.

### Conflict diagnostics (all hosts)

Discovery Files compares the anonymous public `/llms.txt` response byte for byte
with AJNanda's current renderer, including custom overrides and curated eligibility.
It uses a three-second safe HTTP request, at most one redirect, a 1 MiB comparison cap,
and a five-minute cache keyed by expected content, URL, and enabled state.
Changes to expected content therefore invalidate the comparison naturally.
TLS/network errors, redirects, non-200 responses, and oversized bodies do not
claim a match. Local files at WordPress's home path and ABSPATH are also checked
with bounded reads; matching physical files still carry a staleness warning.
Inaccessible server roots, unusual aliases, CDN caches, or files outside those
locations require public-response and server inspection.

A mismatch is detected regardless of whether Hostinger, another plugin, a file,
AJNanda filters, or a cache produced it. The response does not prove the serving
component. Hostinger's signature is only an attribution clue. Diagnostics also
check when AJNanda output is disabled, because another source may still serve it.
No corrective settings or file changes happen automatically. The llms.txt editor
seeds from AJNanda's renderer instead of importing potentially conflicting public
content.

### Verification

PHP syntax and 13 isolated smoke checks passed locally against the reviewed
Hostinger settings classes (platform/plugin absence, opt-in/out, temporary and
migrated domains, derived endpoint, matching/mismatching/oversized responses,
TLS failure, redirect, and signature detection). These checks stub WordPress
storage and HTTP; they do not establish live service behavior.

After placing this theme in your chosen DDEV site, run from that site's directory:

```bash
ddev exec php -l wp-content/themes/ajnanda/inc/search-ai/class-hostinger.php
ddev exec php -l wp-content/themes/ajnanda/inc/search-ai/class-discovery-files.php
ddev wp eval 'echo wp_json_encode(AJNanda_Search_AI_Hostinger::status(), JSON_PRETTY_PRINT), PHP_EOL;'
ddev wp eval 'echo wp_json_encode(AJNanda_Search_AI_Discovery_Files::status(true)["llms_txt"], JSON_PRETTY_PRINT), PHP_EOL;'
ddev wp eval 'echo AJNanda_Search_AI_Discovery_Files::render_llms_txt();' > /tmp/ajnanda-expected-llms.txt
ddev describe
```

Using the site's URL shown by `ddev describe` (replace the example):

```bash
curl --fail --silent --show-error https://example.ddev.site/llms.txt -o /tmp/ajnanda-public-llms.txt
diff -u /tmp/ajnanda-expected-llms.txt /tmp/ajnanda-public-llms.txt
```

Keep TLS verification enabled. A local certificate/loopback error must display as
unverifiable, not as a conflict. WP-CLI may lack `H_PLATFORM` even on Hostinger;
confirm availability in the web admin request too.

Manual DDEV checks: the Hostinger panel is absent without platform/plugin signals;
all existing discovery outputs remain functional; a fixture physical llms.txt in a
